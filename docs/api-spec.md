## 공통 형식

- 시각: ISO 8601, 한국 시간 (`2026-11-02T08:50:00+09:00`). DB에도 KST로 저장한다.
- 금액: 원, 거리: km, 시간: 분, 좌표: WGS84 십진수 (`lat`, `lng`)
- `id`: 모든 리소스의 `id`는 **문자열**로 내려준다 (DB의 BIGINT를 `"12"`처럼). 프론트는 `id`를 문자열로 비교하고, 큰 정수의 JS 정밀도 문제도 피한다.
- `from`, `to`: 장소 이름 (`김해시청`)
- `buffer`: 도착 희망 시각보다 일찍 도착하려는 여유 시간(분)
- 요청 본문은 JSON (`Content-Type: application/json`)

### 인증

서버 세션 방식이다. 이메일 로그인(`POST /api/auth/login`)이나 소셜 로그인 콜백이 성공하면 서버가 세션을 만들고 쿠키를 내려준다. 프론트는 토큰을 다루지 않는다.

| 쿠키 | 값 | 속성 |
| --- | --- | --- |
| `gilit_session` | 무작위 토큰 (서버 DB에는 SHA-256 해시만 저장) | `HttpOnly; SameSite=Lax; Path=/; Max-Age=1209600`(14일), `Secure`는 서버 설정 `COOKIE_SECURE`(운영 `true`). `Domain` 없음 |
| `gilit_oauth` | 소셜 로그인 state·PKCE 값 (HMAC 서명, 암호화 아님) | `HttpOnly; SameSite=Lax; Path=/api/auth; Max-Age=600`(10분). 콜백에서 결과와 상관없이 지운다 |

- 세션 만료는 로그인 시각 + 14일 고정이다. 사용해도 늘어나지 않는다.
- 로그인할 때마다 새 토큰을 발급하고, 요청에 실려 온 이전 세션은 지운다 (세션 고정 방지). 다른 기기의 세션은 그대로 둔다.
- 프론트는 같은 출처(`BASE_URL = "/api"`, 개발은 `http://localhost:8000`)로 요청하므로 `fetch`의 기본값(`credentials: "same-origin"`)으로 쿠키가 실린다. 프론트와 API를 다른 출처로 띄우면 쿠키가 실리지 않는다.
- 로그인 상태는 화면을 열 때 `GET /api/auth/me`로 확인한다. 프론트는 사용자 정보를 메모리에만 두고 `localStorage`의 옛 값(`gilit:user`)은 지운다.

"로그인 필요" API는 세션이 없거나 만료되면 **반드시 `401`** "로그인이 필요합니다."를 돌려준다. 프론트는 `401`만 비로그인으로 보고 그 밖의 코드는 오류로 안내한다. 프론트도 해당 화면(`js/guard.js`의 `PROTECTED_PATHS`)을 로그인 모달로 막지만 화면 흐름용일 뿐이므로, 서버가 반드시 직접 검사한다. 서버 코드에서는 의존성 `require_user`(없으면 401)와 `optional_user`(없으면 `None`)를 쓴다 (`backend/app/api/auth.py`).

### 오류

오류 응답 본문은 `{ "message": "..." }`이다. 프론트는 4xx의 `message`를 그대로 화면에 보여 주고, 5xx와 네트워크 오류는 "잠시 후 다시 시도해 주세요."로 바꾼다. 그래서 4xx `message`는 사용자에게 보여 줄 한국어 문장으로 쓰고, 내부 정보(SQL, 스택)를 넣지 않는다.

| 코드 | 언제 | `message` 예 |
| --- | --- | --- |
| `400` | 입력값 검증 실패 (필수값, 형식, 범위) | 올바른 이메일 형식이 아닙니다. |
| `400` | 요청 본문이 JSON 객체가 아님 (깨진 JSON, UTF-8이 아닌 본문, 배열 등) | 요청 본문은 JSON 객체여야 합니다. |
| `401` | 로그인 필요 API에 세션 없음 | 로그인이 필요합니다. |
| `401` | 이메일 로그인 실패 | 이메일 또는 비밀번호가 올바르지 않습니다. |
| `403` | 상태를 바꾸는 요청(POST·PUT·PATCH·DELETE)의 출처가 허용되지 않음 (아래 "보안 규칙") | 허용되지 않은 출처의 요청입니다. |
| `404` | 리소스가 없거나 내 것이 아님, 없는 경로 | 찾을 수 없습니다. |
| `405` | 허용되지 않은 메서드 | 허용되지 않은 요청 방식입니다. |
| `409` | 이메일 중복 등 충돌 | 이미 가입된 이메일입니다. |
| `422` | 입력은 올바르지만 답을 낼 수 없음 (경로 없음, 제시간 도착 불가) | 경로를 찾을 수 없습니다 |
| `429` | 요청 횟수 제한 초과 (`Retry-After` 헤더에 초) | 요청이 너무 많습니다. 잠시 후 다시 시도해 주세요. |
| `500` | 서버 오류 | 잠시 후 다시 시도해 주세요. |
| `502` | 외부 길찾기 API 오류 (인증, 거부, 연결 실패, 응답 이상) | 길찾기 정보를 가져오지 못했습니다. 잠시 후 다시 시도해 주세요. |
| `503` | 외부 길찾기 API 호출 한도 초과 | 길찾기 API 호출 한도를 초과했습니다. 잠시 후 다시 시도해 주세요. |
| `504` | 외부 길찾기 API 응답 시간 초과 | 길찾기 서버 응답이 늦습니다. 잠시 후 다시 시도해 주세요. |

FastAPI 기본값인 `422` + `detail` 목록은 쓰지 않는다. 입력 검증 실패도 `400` + `message` 하나로 바꿔 보낸다 (`backend/app/api/errors.py`). 5xx의 원인(외부 API 응답 문구, HTTP 코드 등)은 응답에 넣지 않고 서버 로그에만 남긴다.

예외: 소셜 로그인 `start`·`callback`은 브라우저가 페이지째 이동해 오는 주소라 JSON 오류를 보내지 않는다. 어떤 실패든 `/pages/search.html?auth_result=...`로 302 한다 (아래 "소셜 로그인"). 없는 제공자(`/api/auth/naver/start` 등)만 `404` JSON이다.

### CORS

허용 출처는 서버 환경변수 `CORS_ORIGINS`(쉼표 구분)로 정한다. 기본값은 로컬 개발용 `http://localhost:5500`, `http://127.0.0.1:5500`(VS Code Live Server)이다. 세션 쿠키를 보내야 하므로 `allow_credentials`를 켜고, `*`(모든 출처)는 쓸 수 없다. 허용 메서드는 `GET`, `POST`, `PATCH`, `DELETE`, 허용 헤더는 `Content-Type`이다.

다른 사용자의 즐겨찾기처럼 권한이 없는 리소스도 `403` 대신 `404`로 응답해 존재 여부를 드러내지 않는다.

### 보안 규칙

- 모든 쿼리는 파라미터 바인딩(prepared statement)으로 실행한다. 문자열을 이어 붙여 SQL을 만들지 않는다.
- 비밀번호는 bcrypt(cost 12)로 해시해 `users.password_hash`에만 저장한다. 평문 비밀번호를 DB, 로그, 오류 응답에 남기지 않는다. 요청 본문 로깅을 켠다면 `password` 필드를 가린다.
- 횟수 제한: 로그인은 IP별·이메일별 각각 분당 5회, 가입은 IP별 시간당 10회. 넘으면 `429` + `Retry-After`. 서버 프로세스 메모리에 세므로 워커가 하나일 때 정확하다.
- 출처 검사 (CSRF 2차 방어, 1차는 `SameSite=Lax`): `/api/*`의 POST·PUT·PATCH·DELETE는 `Origin`(없으면 `Referer`)의 출처가 같은 호스트이거나 `CORS_ORIGINS`에 있어야 한다. 아니면 `403`. 둘 다 없는 요청(브라우저 밖 클라이언트)은 통과한다. `Content-Type` 검사는 하지 않는다 (프론트의 로그아웃은 본문 없이 보낸다).
- 소셜 로그인 콜백의 인가 코드·state·토큰·쿠키 값은 서버 로그에 남기지 않는다. uvicorn 접근 로그에서도 콜백 쿼리는 `?[REDACTED]`로 가린다.

## 목업 동작

`USE_MOCK = true`이면 `api.js`가 서버 역할 일부를 대신한다. 실제 서버는 아래 값을 직접 계산해서 돌려준다.

- 경로: `arriveTime`은 `arrive - buffer`, `departTime`은 `arriveTime - durationMin`
- 그래프: 예시 `js/mock/routeGraph.json`을 쓴다 (`routeId`는 예시 카드 `route-1/2/3`). 실제 서버는 `card`의 id를 `routeId`로 돌려준다 (아래 `GET /api/routes/graph`)
- 기록·통계: 가장 최근 날짜가 오늘이 되도록 날짜를 옮긴다
- 장소 검색: 앞뒤 공백을 제거한 `q`가 `name` 또는 `address`에 포함된 항목을 돌려준다
- 회원가입·로그인: 계정을 `localStorage`의 `gilit:mock:users`에 저장한다. 비밀번호는 평문이 아닌 SHA-256 값으로 두지만, 브라우저 안의 흉내일 뿐이다. 서버는 bcrypt를 쓴다. 로그인 상태는 탭의 `sessionStorage`(`gilit:mock:session`)에만 둔다.
- 소셜 로그인: 프론트 mock은 없다. 서버 없이 시험하려면 서버를 `AUTH_STORE=memory OAUTH_MOCK=1`로 띄운다 (외부 호출 없이 `start`가 곧바로 콜백으로 이동한다. Google은 `mock.google@example.com`, 카카오는 이메일 없는 고정 프로필).

## 길찾기 (로그인 불필요)

### GET /api/places?q=

백엔드가 카카오 로컬 키워드 검색을 중계한다. 키워드 결과가 없으면 주소 검색을 시도한다. REST 키는 서버에서만 관리한다.

요청: `GET /api/places?q=김해시청`

`q`는 장소명 또는 주소 검색어다. 프론트는 앞뒤 공백을 제거해 전달한다. 응답은 장소명(`name`)과 주소(`address`)를 포함한 배열이며, 결과가 없으면 빈 배열이다. 목업은 제공된 예시 장소 범위 안에서 이름·주소 부분 일치로 검색한다. 실제 검색은 기존 `/api/places` 계약을 사용하며 백엔드 구현은 별도 범위다.

```json
[
  { "id": "place-1", "name": "김해시청", "address": "경상남도 김해시", "lat": 35.2285, "lng": 128.8894 }
]
```

### POST /api/departure (구현됨)

로그인: 불필요. 구현: `backend/app/api/departure.py`, 엔진: `backend/app/departure/`

장소 검색 결과의 좌표로 권장 출발시각 하나를 계산한다. 목표 도착시각(`arrive_at - buffer_min`)까지 도착하는 가장 늦은 출발시각을 분 단위로 찾는다. 경로 목록·통행료·경로선은 돌려주지 않는다 (그건 아래 `GET /api/routes`). 추천 경로 기준이며, `GET /api/routes`의 `recommend` 카드와 같은 카카오 조회 캐시를 쓴다.

**[해민과 합의 필요]** 이 API는 요청·응답 필드를 snake_case로 쓴다. 다른 API와 프론트는 camelCase(`departTime`)다. 아래 "해민과 정할 것" 참고.

요청:

```json
{
  "origin": { "name": "김해시청", "lat": 35.2285, "lng": 128.8894 },
  "destination": { "name": "동의대학교", "lat": 35.1441, "lng": 129.0336 },
  "arrive_at": "2026-11-06T09:00:00+09:00",
  "buffer_min": 10,
  "travel_mode": "car"
}
```

| 필드 | 필수 | 규칙 | 오류 `message` (400) |
| --- | --- | --- | --- |
| `origin`, `destination` | 예 | `name`, `lat`, `lng`가 있는 객체 | 출발지가 필요합니다. / 출발지는 name, lat, lng가 있는 객체여야 합니다. |
| `*.name` | 예 | 앞뒤 공백 제거 후 1~100자 | 출발지 장소 이름은 1~100자로 입력해 주세요. |
| `*.lat` | 예 | -90 ~ 90 | 출발지 위도는 -90~90 사이의 숫자여야 합니다. |
| `*.lng` | 예 | -180 ~ 180 | 목적지 경도는 -180~180 사이의 숫자여야 합니다. |
| `arrive_at` | 예 | ISO 8601 문자열. 시간대가 없으면 한국 시간으로 본다. 지금보다 미래 | 도착 희망 시각은 ISO 8601 형식이어야 합니다 (예: 2026-11-06T09:00:00+09:00). / 도착 희망 시각이 이미 지났습니다. |
| `buffer_min` | 아니오 (기본 0) | `0`, `5`, `10`, `15` 중 하나인 정수 (`"10"`, `true`는 거부) | 여유시간은 0, 5, 10, 15분 중 하나여야 합니다. |

서버 동작:

- 카카오 어댑터는 서버를 띄울 때 하나만 만들어 모든 요청이 함께 쓴다. 같은 (출발지, 목적지, 출발시각(분), 이동수단) 조회는 메모리 캐시로 다시 부르지 않고, 캐시는 `ROUTE_CACHE_TTL_SEC`(기본 600초)이 지나면 버린다.
- 카카오 일일 쿼터는 5,000건이다. 요청 하나당 최대 8회라 하루 약 625회 계산까지 된다.
- 이 API는 `search_history`에 저장하지 않는다. 검색 기록은 `GET /api/routes`가 성공했을 때 서버가 저장한다 (아래 "검색 기록").

### GET /api/routes (구현됨, 경로 비교 F5)

로그인: 불필요. 구현: `backend/app/api/routes.py`(API), `backend/app/routing.py`의 `compare_routes`(비교 서비스), 엔진: `backend/app/departure/`

경로 옵션마다 출발시각 역산 엔진을 돌려, 옵션별 권장 출발시각·예상 도착시각·소요시간·거리·통행료·경로선을 카드 배열로 돌려준다. 필드는 camelCase다 (프론트 `getRoutes`, `js/mock/routes.json`).

요청:

```
GET /api/routes?from=김해시청&to=동의대학교&arrive=2026-11-13T09:00:00%2B09:00&buffer=10

```

| 파라미터 | 필수 | 규칙 | 오류 `message` (400) |
| --- | --- | --- | --- |
| `from`, `to` | 예 | 앞뒤 공백 제거 후 1~100자, 서로 달라야 한다 | 출발지가 필요합니다. / 출발지는 1~100자로 입력해 주세요. / 출발지와 다른 목적지를 입력해 주세요. |
| `arrive` | 예 | ISO 8601. 시간대가 없으면 한국 시간. `+`는 `%2B`로 보낸다. 지금보다 미래 | 도착 희망 시각은 ISO 8601 형식이어야 합니다 (예: 2026-11-06T09:00:00+09:00). / 도착 희망 시각이 이미 지났습니다. |
| `buffer` | 아니오 (기본 0) | `0`, `5`, `10`, `15` | 여유시간은 0, 5, 10, 15분 중 하나여야 합니다. |
| `fromLat`, `fromLng` | 아니오 | 함께 보낸다. 위도 -90~90, 경도 -180~180, NaN 불가 | 출발지 위도와 경도를 함께 보내 주세요. / 출발지 위도는 -90~90 사이의 숫자여야 합니다. |
| `toLat`, `toLng` | 아니오 | 위와 같다 | 목적지 위도와 경도를 함께 보내 주세요. / 목적지 경도는 -180~180 사이의 숫자여야 합니다. |

좌표가 있으면 그 좌표를 쓴다. 좌표가 없으면(좌표가 생기기 전의 공유 링크) 서버가 장소 검색으로 이름을 하나의 장소로 확정한다. 확정하지 못하면 422다.

응답: `200` 카드 배열. 카드 순서는 서버 설정 `ROUTE_COMPARE_OPTIONS` 순서(기본 추천, 최단시간, 최단거리, 무료도로)이고 **1~4개**다.

```json
[
  {
    "id": "recommend",
    "options": ["recommend", "time"],
    "label": "추천",
    "name": "남해고속도로(순천-부산) 경유",
    "departTime": "2026-11-13T08:19:00+09:00",
    "arriveTime": "2026-11-13T08:49:10+09:00",
    "durationMin": 31,
    "distanceKm": 21.97,
    "toll": 1300,
    "fuel": null,
    "bufferApplied": true,
    "converged": true,

      { "lat": 35.2285, "lng": 128.8894 },
      { "lat": 35.1441, "lng": 129.0336 }
    ],
    "aiSummary": { "title": "추천 경로", "text": "소요시간·거리·통행료·경로선은 같은 상세 길찾기 응답 기준입니다." }

```

위 값은 2026-11-12에 실제 카카오로 조회한 첫 카드다. `path`는 실제로 수백 개 좌표이고 여기서는 줄였다.

| 필드 | 설명 |
| --- | --- |
| `id` | 카드를 만든 경로 옵션: `recommend`(추천), `time`(최단시간), `distance`(최단거리), `free`(무료도로) |
| `options` | 이 카드에 합쳐진 옵션. 같은 길로 확인된 옵션은 앞 카드에 합친다 (예: 추천과 최단시간이 같은 길이면 `["recommend", "time"]`, 이때 `time` 카드는 따로 없다) |
| `label` | `id`의 이름: 추천, 최단시간, 최단거리, 무료도로 |
| `name` | 경로에서 가장 긴 도로 이름 + " 경유". 도로 이름이 없으면 `label` |
| `departTime` | 권장 출발시각 (한국 시간, 분 단위) |
| `arriveTime` | 예상 도착시각 = `departTime` + 상세 경로 소요시간 (초 단위) |
| `durationMin` | 예상 소요시간(분, 올림) |
| `distanceKm` | 거리(km) |
| `toll` | 통행료(원). 카카오가 주지 않으면 `null` (화면은 "미제공") |
| `fuel` | 예상 유류비. 아직 제공하지 않아 항상 `null` |
| `bufferApplied` | 여유시간을 반영했는지. 요청이 0분이거나 지금 출발해도 여유를 둘 수 없으면 `false` (여유 없이 계산한 결과) |
| `converged` | `false`면 조회 한도에 걸려 확인된 시각 중 가장 늦은 것을 돌려준 것. 실제 답보다 이르거나 같아서 늦지 않는다 |
| `dataSource` | `kakao` 또는 `mock` (서버 `ROUTE_PROVIDER`) |
| `path` | 지도에 그릴 경로 좌표 `[{lat, lng}]`. 두 개 이상 |
| `aiSummary` | 화면 호환용 고정 안내 `{title, text}`. AI 요약은 아직 없다 |

`durationMin`, `distanceKm`, `toll`, `path`, `name`, `arriveTime`은 모두 **같은 상세 경로 응답 하나**에서 나온다. 다른 옵션이나 다른 출발시각의 값을 섞지 않는다.

오류:

| 코드 | 언제 | `message` |
| --- | --- | --- |
| `400` | 위 표의 입력 오류, 지난 도착 희망 시각 | 표 참고 |

| `422` | 모든 옵션이 실패 (첫 옵션의 오류를 돌려준다) | 지금 출발해도 도착 희망 시각까지 도착할 수 없습니다. / 해당 조건으로 자동차 경로를 찾을 수 없습니다. 등 |

일부 옵션만 실패하면(경로 없음, 제시간 도착 불가, 무료도로인데 통행료가 있음) **그 카드만 빼고 200**을 돌려준다. 빠진 옵션과 이유는 응답에 넣지 않고 서버 로그(`app.api` 로거)에만 남긴다. 통행료 없는 길이 없는 경우는 INFO, 그 밖은 WARNING이다. 공급자 오류(5xx)는 남은 옵션을 부르지 않고 바로 돌려준다. 실제 조회가 실패해도 예시 경로로 대체하지 않는다.

서버 동작:

- 옵션마다 역산 엔진이 요약 조회(`summary=true`, 경로 좌표 없음)로 출발시각을 찾고(옵션당 최대 `ROUTE_COMPARE_MAX_CALLS`, 기본 6회), 확정된 출발시각에 상세 경로(`road_details=true`)를 한 번 받아 카드를 만든다.
- 중복: 엔진의 첫 조회(같은 출발시각의 소요시간·거리·통행료)가 이미 만든 카드와 같으면 탐색을 멈추고 상세 좌표 1회로 같은 길인지 확인한다. 같으면 앞 카드의 `options`에 합친다. 첫 조회는 달라도 상세 좌표가 같으면 역시 합친다.
- 무료도로(`free`)는 카카오 `avoid=toll`이다. 결과에 통행료가 있으면 카드에서 뺀다.
- 상세 경로의 소요시간이 요약과 다르면 상세 값 기준으로 출발시각을 앞당긴다 (늦게 안내하지 않는다). 더 짧으면 그대로 둔다.
- 요청당 카카오 호출: 옵션마다 요약 최대 6회 + 상세 1~2회, 최악 32회. 2026-11-12 실측(김해시청 → 동의대학교, 다음 날 09:00, 여유 10분)은 카드 3개(추천·최단시간이 합쳐짐), **18회**였다. 일일 쿼터 5,000건이면 하루 약 270회 비교다.
- 캐시: 카카오 요약 조회는 Provider 캐시(`ROUTE_CACHE_TTL_SEC`, 기본 600초, 옵션별)를 쓴다. `/api/departure`와 추천 옵션은 같은 캐시를 쓴다. 성공한 전체 응답은 같은 시간 동안 프로세스 메모리에 최대 64건 저장한다. 키는 출발지·목적지 이름과 좌표, 도착 희망 시각, 여유시간이고, 응답 헤더 `X-Gilit-Route-Cache: HIT|MISS`로 확인한다. 출발시각이 지난 결과·실패는 재사용하지 않는다. 캐시는 서버 재시작 시 사라지고 프로세스 간 공유하지 않는다. 응답에는 `Cache-Control: no-store`가 붙는다.

mock 모드 (`ROUTE_PROVIDER=mock`):

- 카카오 없이 동작한다. `dataSource`는 `mock`이고, 옵션마다 거리·속도·혼잡·통행료를 다르게 둔 가짜 데이터(`MockRouteProvider`)로 카드 4개를 만든다. 경로선은 출발지와 목적지를 잇는 가짜 곡선이고, `name`은 "가상 고속도로 경유"처럼 나온다. 실제 교통 정보와 무관하다.
- mock 모드에는 장소 검색이 없으므로 **좌표 파라미터가 필요하다**. 이름만 오면 422다. `GET /api/places`는 mock 모드에서 502다.
- 프론트 `USE_MOCK_ROUTES=true`일 때는 서버를 부르지 않고 `js/mock/routes.json`을 쓴다. 이 둘은 다른 mock이다.

### GET /api/routes/graph (구현됨, 소요시간 그래프 SFR-006)

로그인: 불필요. 구현: `backend/app/api/routes.py`(API), `backend/app/route_graph.py`(슬롯 조회 서비스). 검색 기록은 남기지 않는다.

`GET /api/routes`로 받은 카드마다, 권장 출발시각 앞뒤 슬롯에 출발했을 때의 소요시간을 돌려준다. 프론트(`getRouteGraph`)는 `/api/routes` 응답을 받은 뒤 검색 하나에 한 번 부른다. 카드를 바꿔도 다시 부르지 않는다.

요청:

```
GET /api/routes/graph?from=김해시청&to=동의대학교&arrive=2026-11-13T09:00:00%2B09:00
                     &fromLat=35.2285&fromLng=128.8894&toLat=35.1441&toLng=129.0336
                     &card=recommend%402026-11-13T08:19:00%2B09:00&card=distance%402026-11-13T08:12:00%2B09:00
```

| 파라미터 | 필수 | 규칙 | 오류 `message` (400) |
| --- | --- | --- | --- |
| `from`, `to`, `arrive`, 좌표 4개 | | `GET /api/routes`와 같다 (좌표는 위도·경도를 함께, 지난 `arrive`는 400) | 위 `GET /api/routes` 표 참고 |
| `card` | 예, **1~4개 반복** | `<경로 id>@<권장 출발시각>`. `/api/routes` 카드의 `id`와 `departTime`을 그대로 잇는다. 마지막 `@`를 기준으로 나눈다 | card는 1~4개 보내 주세요. / card는 <경로 id>@<출발시각> 형식이어야 합니다 (…). |
| └ id | | 서버 `ROUTE_COMPARE_OPTIONS`의 옵션 키(기본 `recommend`, `time`, `distance`, `free`). 같은 id가 두 번 오면 거절 | card의 경로 id는 recommend, time, distance, free 중 하나여야 합니다. / 같은 경로 id의 card가 두 번 있습니다. |
| └ 출발시각 | | 시간대가 있는 ISO 8601(`+`는 `%2B`, `Z` 가능). `arrive` 전 24시간 안(`arrive − 24시간 ≤ 시각 < arrive`). **지난 시각도 거절하지 않는다** (지난 슬롯만 뺀다) | card의 출발시각은 시간대가 있는 ISO 8601 형식이어야 합니다 (…). / card의 출발시각은 도착 희망 시각 전 24시간 안이어야 합니다. |
| `buffer` | 아니오 | 받지만 **쓰지 않는다**. 어떤 값이어도 오류가 아니다 (프론트가 검색 조건을 그대로 보낸다) | - |

좌표가 없으면 `/api/routes`처럼 장소 검색으로 이름을 확정한다 (못 하면 422).

응답: `200`, 감싸지 않은 **배열**. 순서는 요청한 `card` 순서다.

```json
[
  {
    "routeId": "recommend",
    "points": [
      { "departTime": "2026-11-13T07:34:00+09:00", "durationMin": 29 },
      { "departTime": "2026-11-13T07:49:00+09:00", "durationMin": 30 },
      { "departTime": "2026-11-13T08:04:00+09:00", "durationMin": 31 },
      { "departTime": "2026-11-13T08:19:00+09:00", "durationMin": 31 },
      { "departTime": "2026-11-13T08:34:00+09:00", "durationMin": 30 },
      { "departTime": "2026-11-13T08:49:00+09:00", "durationMin": 28 },
      { "departTime": "2026-11-13T09:04:00+09:00", "durationMin": 27 }
    ]
  }
]
```

위 숫자는 형식 설명용 예시다. 실제 교통 예측이 아니다.

| 필드 | 설명 |
| --- | --- |
| `routeId` | 요청한 `card`의 id 그대로 (= 같은 검색의 `/api/routes` 카드 `id`, 합쳐진 카드는 그 카드의 `id`) |
| `points[].departTime` | 슬롯 출발시각. 한국 시간 `+09:00`, 분 단위. 시간순 |
| `points[].durationMin` | 그 시각에 출발했을 때의 예상 소요시간(분, 올림, 0 이상). 요약 조회(`summary=true`) 값이라 카드의 `durationMin`(상세 조회)과 1분쯤 다를 수 있다 |

슬롯:

- 카드 출발시각(분 단위 내림) 기준 **15분 간격, −45분 ~ +45분, 카드당 7개** (`GRAPH_SLOTS_BEFORE`·`GRAPH_SLOTS_AFTER`·`GRAPH_SLOT_INTERVAL_MIN`).
- **지금 이전 슬롯은 뺀다.** 모든 슬롯이 지났으면 `[]`.
- **`arrive` 이후(`arrive` 이상) 슬롯도 뺀다.** 뺀 슬롯은 호출 수·일일 예산·13개 상한에 세지 않고, 슬롯이 모두 빠진 카드는 응답 항목에서 뺀다.
- 요청 하나의 슬롯 조회는 **최대 13개**다. 넘으면 권장 출발시각에 가까운 슬롯부터 카드를 번갈아 고른다. 그래서 모든 카드에 권장 출발시각과 ±15분 점이 남고, 카드 2개면 두 번째 카드의 +45분, 카드 4개면 카드당 3~4개가 된다.
- 한 요청 안에서 같은 (출발지, 목적지, 분, 경로 옵션) 조회가 겹치면 한 번만 부른다. 지금은 카드 id와 옵션이 1:1이라 겹치지 않는다.

부분 실패와 오류:

- 일부 슬롯이 실패하면 **그 점만**, 한 카드의 점이 하나도 없으면 **그 항목만** 빼고 `200`이다. 이유는 서버 로그(`app.route_graph`, 장소 정보 없이 개수와 오류 종류)에만 남긴다.
- 조회할 슬롯이 있었는데 점이 하나도 없을 때만 오류다. 우선순위: 호출 한도 → `503`, 시간 초과 → `504`, 그 밖에는 첫 실패를 기존 매핑으로 (`502` 공급자 오류, `422` 경로 없음).

| 코드 | 언제 | `message` |
| --- | --- | --- |
| `400` | 위 표의 입력 오류, 지난 도착 희망 시각 | 표 참고 |
| `422` | 장소를 확정하지 못함, 모든 슬롯에서 경로 없음 | 장소를 하나로 확인할 수 없어요. … / 해당 조건으로 자동차 경로를 찾을 수 없습니다. 등 |
| `502` | 모든 슬롯이 카카오 인증 실패·요청 거부·연결 실패 | 길찾기 정보를 가져오지 못했습니다. 잠시 후 다시 시도해 주세요. |
| `503` | 카카오 호출 한도 초과 | 길찾기 API 호출 한도를 초과했습니다. 잠시 후 다시 시도해 주세요. |
| `503` | 그래프 일일 호출 예산 소진 (카카오를 부르지 않는다. 장소 검색 포함) | 오늘 소요시간 그래프 조회 한도를 모두 사용했습니다. 내일 다시 시도해 주세요. |
| `504` | 모든 슬롯이 카카오 응답 시간 초과 | 길찾기 서버 응답이 늦습니다. 잠시 후 다시 시도해 주세요. |
| `504` | 서버 시간 예산 안에 점을 하나도 받지 못함 | 소요시간 그래프를 제시간에 계산하지 못했습니다. 잠시 후 다시 시도해 주세요. |

서버 동작:

- **캐시하지 않는다.** 카카오모빌리티 약관상 길찾기 응답은 임시로도 캐시할 수 없다. 그래서 그래프는 응답을 저장하지 않고(같은 요청도 매번 조회), 슬롯 조회는 카카오 Provider의 메모리 캐시(`ROUTE_CACHE_TTL_SEC`)를 읽지도 쓰지도 않는다. `/api/routes`·`/api/departure`의 기존 캐시 동작은 바꾸지 않았다 (아래 "열린 문제"). 응답에는 `Cache-Control: no-store`가 붙는다.
- 동시 조회: 슬롯은 작업 스레드 `GRAPH_MAX_WORKERS`(기본 4)개로 동시에 조회한다. 작업 스레드는 프로세스에 하나의 풀로 두고 모든 그래프 요청이 함께 쓴다. 카카오 HTTP 세션은 작업 스레드마다 따로 쓴다 (`requests.Session`은 스레드 안전을 보장하지 않는다).
- 시간 예산: 요청 하나에 `GRAPH_TIME_BUDGET_SEC`(기본 8초, 프론트 제한 10초). 넘으면 그때까지 받은 점만 돌려주고 남은 조회는 시작하지 않는다. 이미 시작한 조회는 카카오 제한 시간(10초)까지 뒤에서 끝나고 결과는 버린다.
- 일일 예산: 그래프 전용 카카오 호출 `GRAPH_DAILY_CALL_BUDGET`(기본 1,500회/일, KST 날짜가 바뀌면 0부터). 실제로 부른 조회만 센다 (합쳐진 조회·건너뛴 슬롯은 세지 않는다). 다 쓰면 카카오를 부르지 않고 `503`. 프로세스 메모리에 세므로 워커가 하나일 때 정확하고, 재시작하면 0부터다. 카카오 일일 쿼터(5,000건)는 `/api/routes`와 함께 쓴다.
- 요청당 카카오 호출: 슬롯 최대 13회 (+ 좌표가 없으면 장소 검색). 1,500회면 하루 약 115~215회 그래프다.
- mock 모드(`ROUTE_PROVIDER=mock`)도 같은 규칙으로 가짜 소요시간을 돌려준다 (좌표 필요).

열린 문제:

- `/api/routes`·`/api/departure`는 지금도 카카오 응답을 Provider 캐시와 전체 응답 캐시(`RouteResultCache`)에 저장한다. 약관과 맞는지 따로 확인해야 한다. 이번에는 그래프만 캐시 없이 만들었다.
- 프론트는 아직 `card`를 보내지 않는다 (`frontend/js/graphData.js`). `card`가 없으면 이 API는 `400`을 주므로, 프론트가 `card`를 보내기 전까지 그래프는 "불러오지 못했습니다"로 표시된다 (로컬 예시 그래프는 `404`일 때만 나온다).

## 회원 (`users`, `social_accounts`)

### 사용자 객체

회원 API가 돌려주는 사용자 정보다.

```json
{ "id": "1", "name": "길잇", "email": "user@example.com", "provider": "email" }
```

- `id`: 문자열 (`users.id`)
- `name`: `users.nickname`. 소셜 가입자는 제공자 이름(Google `name`, 카카오 `kakao_account.profile.nickname`)을 20자로 자른 값이고, 없으면 "길잇 사용자"
- `email`: 소문자. **`null`일 수 있다** (이메일을 주지 않거나 검증되지 않은 이메일을 준 소셜 가입자, 주로 카카오)
- `provider`: **이번 세션의 로그인 방식** `email` | `google` | `kakao` (`sessions.login_provider`). 가입 방법이 아니다.

### 검증 규칙

프론트(`js/components/authModal.js`)도 같은 규칙으로 먼저 검사하지만, 서버가 다시 검사한다.

| 필드 | 규칙 | 오류 `message` |
| --- | --- | --- |
| `name` | 앞뒤 공백 제거 후 2~20자 | 이름은 2~20자로 입력해 주세요. |
| `email` | 앞뒤 공백 제거·소문자 변환 후 이메일 형식, 254자 이하 | 올바른 이메일 형식이 아닙니다. |
| `password` | 8~64자, 영문과 숫자를 모두 포함, UTF-8 72바이트 이하 (bcrypt 한계) | 비밀번호는 영문과 숫자를 포함해 8~64자로 입력해 주세요. |
| `agreeTerms`, `agreePrivacy` | 둘 다 `true` | 필수 약관에 모두 동의해 주세요. |

### 소셜 계정 처리 (같은 이메일)

이메일이 있는 계정은 이메일 하나당 하나다 (`users.email` UNIQUE, NULL은 여러 개 허용). **계정을 이메일로 자동 연결하지 않는다.**

| 상황 | 처리 |
| --- | --- |
| 이메일 회원가입, 같은 이메일 계정이 이미 있음 (가입 방법 무관) | `409` "이미 가입된 이메일입니다." |
| 소셜 로그인, `social_accounts`에 `(provider, provider_user_id)`가 있음 | 그 계정으로 로그인. 제공자 쪽 이메일·이름이 바뀌어도 DB는 바꾸지 않는다 |
| 소셜 첫 로그인, **검증된** 이메일이 기존 계정과 같음 (이메일 가입이든 다른 소셜이든) | 계정을 만들지도 연결하지도 않는다 → `auth_result=email_exists` |
| 소셜 첫 로그인, 이메일이 없거나 검증되지 않음 | `email` NULL로 새 계정 (미검증 이메일은 저장하지 않는다. 기존 계정과 같아도 별도 계정) |
| 소셜 첫 로그인, 검증된 새 이메일 | 그 이메일로 새 계정 |

- `provider_user_id`: Google `sub`, 카카오 회원번호 `id`(문자열로 저장). 같은 값이라도 제공자가 다르면 다른 계정이다.
- 검증된 이메일: Google은 `email_verified`가 참, 카카오는 `is_email_valid`와 `is_email_verified`가 모두 참일 때.
- 자동 연결하지 않는 이유: 이메일 회원가입은 이메일 소유를 확인하지 않는다. 남이 피해자 이메일로 먼저 가입해 두면, 피해자의 소셜 로그인이 그 계정에 붙어 공격자도 같은 계정에 들어갈 수 있다. 계정 연결은 나중에 로그인한 상태의 "내 정보"에서만 제공한다.
- 소셜 가입은 `users`(`password_hash` NULL)와 `social_accounts`를 한 트랜잭션으로 넣는다. `agreed_at`은 가입 시각이다 (로그인 모달의 "계속하면 서비스 이용약관 및 개인정보 처리방침에 동의하게 됩니다." 안내를 동의로 본다).
- 같은 소셜 계정으로 동시에 첫 로그인해도 계정은 하나만 생기고 모두 그 계정으로 로그인된다 (UNIQUE 위반이면 다시 조회한다).
- 소셜 전용 계정은 이메일 로그인을 할 수 없다 (`401`, 계정 없음과 같은 응답).

### POST /api/auth/signup

로그인: 불필요

요청:

```json
{ "name": "길잇", "email": "user@example.com", "password": "gilit1234", "agreeTerms": true, "agreePrivacy": true }
```

응답: `201` + 사용자 객체 (`provider`는 `email`). 가입만 하고 로그인 세션은 만들지 않는다. 프론트는 로그인 화면으로 돌아가 이메일을 채워 둔다.

```json
{ "id": "1", "name": "길잇", "email": "user@example.com", "provider": "email" }
```

DB: `users`에 `email`(소문자), `password_hash`(bcrypt), `nickname`(= `name`), `agreed_at`(= 지금)을 넣는다. 중복 검사는 먼저 조회하지 말고 INSERT에서 UNIQUE 위반(MySQL 오류 1062)을 받아 `409`로 바꾼다. 동시에 가입해도 하나만 성공한다.

오류: `400` 검증 실패 (위 표의 `message`), `403` 출처 검사, `409` "이미 가입된 이메일입니다.", `429` 횟수 제한 (IP별 시간당 10회. 검증에 실패한 요청은 세지 않는다)

### POST /api/auth/login

로그인: 불필요

요청:

```json
{ "email": "user@example.com", "password": "gilit1234" }
```

응답: `200` + `gilit_session` 쿠키 + 사용자 객체 (`provider`는 `email`). `users.last_login_at`을 지금 시각으로 갱신한다. 이메일은 앞뒤 공백 제거·소문자로 비교한다.

오류: `400` 이메일 형식 오류·비밀번호 없음 ("비밀번호를 입력해 주세요."), `403` 출처 검사, `429` 횟수 제한 (IP별·이메일별 분당 5회, 성공한 로그인도 센다).
`401` "이메일 또는 비밀번호가 올바르지 않습니다."는 계정이 없을 때, 소셜 전용 계정(`password_hash` NULL)일 때, 비밀번호가 틀렸을 때 모두 같은 응답이다. 계정이 없거나 소셜 전용일 때도 같은 cost의 더미 해시로 bcrypt 비교를 한 번 수행해 응답 시간으로 계정 존재가 드러나지 않게 한다.

### POST /api/auth/logout

로그인: 불필요 (세션이 없어도 `204`). 본문과 `Content-Type` 없이 보내도 된다.

세션을 지우고 쿠키를 만료시킨다 (`Max-Age=0`). 응답: `204` (본문 없음). 다른 출처에서 보내면 `403`이고 세션은 그대로다.

### GET /api/auth/me

로그인: **필요**

새로고침 등으로 서버 세션 기준의 로그인 상태를 확인할 때 쓴다. 응답: `200` + 사용자 객체

오류: `401` "로그인이 필요합니다." (세션 없음, 만료, 모르는 토큰 모두)

### 소셜 로그인 (Google, 카카오)

제공자는 `google`, `kakao` 두 가지다. 서버에 설정되지 않은 제공자는 `start`가 곧바로 `auth_result=failed`로 돌려보낸다. 그 밖의 이름(`naver` 등)은 `404`.

**`GET /api/auth/{provider}/start`** — 프론트는 `fetch`가 아니라 페이지 이동(`location.assign`)으로 연다.

1. 서버가 state(무작위)와 PKCE verifier를 만들어 `gilit_oauth` 쿠키(HMAC-SHA256 서명, 10분)에 담는다.
2. 제공자 인증 화면으로 `302`. Google은 PKCE(S256)와 `prompt=select_account`를 붙인다. 카카오는 공식 문서에 PKCE 파라미터가 없어 state만 쓴다 (client secret으로 토큰 교환).

**`GET /api/auth/{provider}/callback`** — 제공자가 사용자를 돌려보내는 주소. 콘솔에 `{OAUTH_REDIRECT_BASE}/api/auth/{provider}/callback`(개발: `http://localhost:8000/api/auth/google/callback`, `.../kakao/callback`)으로 등록한다.

1. `error=access_denied`(사용자가 취소)면 `cancelled`. 다른 `error`는 `failed`.
2. `gilit_oauth` 쿠키의 서명·만료·제공자를 확인하고, 쿠키의 state와 쿼리의 `state`를 비교한다. 쿠키가 없거나(다른 브라우저에서 연 링크) 한 번 쓴 state면 `failed`.
3. 인가 코드를 토큰으로 바꾸고 프로필(`sub`/`id`, 이메일, 검증 여부, 이름)을 가져온다. 실패하면 `failed`.
4. 위 "소셜 계정 처리"대로 로그인하거나 가입한다. 세션을 만들고 `gilit_session`을 내려준다 (이전 세션은 지운다).
5. `/pages/search.html?auth_result={결과}`로 `302`. `gilit_oauth`는 결과와 상관없이 지운다.

| `auth_result` | 뜻 | 세션 | 프론트 안내 (예) |
| --- | --- | --- | --- |
| `success` | 로그인(또는 첫 가입) 성공 | 만듦 | 없음. `/api/auth/me` 확인 후 원래 화면으로 이동 |
| `cancelled` | 사용자가 제공자 화면에서 취소 | 없음 | 소셜 로그인이 취소되었습니다. |
| `email_exists` | 검증된 이메일이 다른 방법으로 가입한 계정과 같음 | 없음 | 이미 가입된 이메일입니다. 기존에 쓰던 방법으로 로그인해 주세요. |
| `failed` | 그 밖의 모든 실패 (state 검사, 토큰 교환, 설정 없음, 서버 오류) | 없음 | 소셜 로그인에 실패했습니다. 다시 시도해 주세요. |

실패 사유는 서버 로그에만 남긴다 (인가 코드·state·토큰 값은 남기지 않는다). 콜백은 `Cache-Control: no-store`다.

## 즐겨찾기 (`favorite_places`, 로그인 필요, **구현됨**)

모든 즐겨찾기 API는 로그인이 필요하고(`require_user`) 세션 사용자의 것만 다룬다. 쿼리는 언제나 `WHERE id = ? AND user_id = ?`다.

- `401` "로그인이 필요합니다.": 세션 없음·만료. 프론트는 비로그인이면 **호출하지 않는다** (홈 화면 포함).
- `404` "찾을 수 없습니다.": `id`가 없거나, 숫자가 아니거나(`abc`, `-1`, `1.0`), 남의 것이거나, 이미 지운 것. 남의 데이터가 있는지 드러내지 않으려고 모두 같은 응답이다.
- `409`: "이미 같은 이름의 즐겨찾기가 있습니다." 또는 "즐겨찾기는 최대 20개까지 저장할 수 있습니다."

필드 매핑: `name` = `place_name`(사용자가 붙인 별칭), `type` = `label`, `address` = `address`, `lat`·`lng` = 같은 이름. `id`는 문자열.

| 필드 | 규칙 (서버가 직접 검사, 실패하면 `400`) | 오류 `message` |
| --- | --- | --- |
| `name` | 앞뒤 공백 제거·연속 공백 하나로, 제어·서식 문자 불가, 1~100자 | 장소 이름은 1~100자로 입력해 주세요. |
| `type` | `집` `학교` `회사` `기타` 중 하나. POST에서 생략하면 `기타` | 분류는 집, 학교, 회사, 기타 중 하나여야 합니다. |
| `address` | 255자 이하, 빈 값이면 `null` | 주소는 255자 이하로 입력해 주세요. |
| `lat`, `lng` | 둘 다 보내거나 둘 다 생략. 숫자(문자열 불가), -90~90 / -180~180. 소수 7자리로 맞춘다 | 위도와 경도는 함께, 올바른 범위의 숫자로 보내 주세요. |

- 같은 이름: 같은 사용자 안에서 별칭은 하나다. **대소문자·악센트·전각을 구분하지 않는다** (`Home`=`home`, `Café`=`cafe`, `Ａ`=`A`). 다른 사용자, 같은 좌표의 다른 이름은 허용.
- 개수: 사용자당 최대 20개. 동시에 추가해도 넘지 않는다.

### POST /api/favorites

```json
{ "name": "집", "address": "경상남도 김해시 내외중앙로 47", "type": "집", "lat": 35.2285, "lng": 128.8894 }
```

- `lat`·`lng`가 있으면 그대로 쓴다 (**권장**: 장소 검색에서 고른 좌표를 함께 보낸다).
- 없으면 서버가 `address`(없으면 `name`)로 장소를 검색해 **결과가 정확히 하나일 때만** 그 좌표를 쓴다 (이름이 정확히 같은 결과가 있으면 그것). 없거나 여러 개이거나 서버가 mock 길찾기 모드면 `400` "장소 위치를 찾을 수 없습니다. 장소를 검색해서 선택해 주세요." 길찾기 API 장애는 `502`·`503`·`504`.

응답: `201` + 즐겨찾기 하나 (위와 같은 형식). 오류: `400`, `401`, `403`(출처), `409`

### PATCH /api/favorites?id=

보낸 필드만 바꾼다. 이름·분류는 따로 바꿀 수 있고, **장소를 바꿀 때는 `address`·`lat`·`lng`를 함께** 보낸다 (`address`는 `null` 가능). 좌표 없이 주소만 바꾸는 것은 안 된다 (서버가 다시 찾지 않는다).

```json
{ "name": "우리 집", "type": "집" }
{ "address": "부산광역시 동구 중앙대로 206", "lat": 35.1151, "lng": 129.0414 }
```

응답: `200` + 수정된 즐겨찾기. 오류: `400`("장소를 바꿀 때는 address, lat, lng를 함께 보내 주세요.", "바꿀 내용이 없습니다." 등), `401`, `404`, `409`(다른 즐겨찾기와 같은 이름. 자기 이름의 대소문자만 바꾸는 것은 된다)

## 검색 기록 (`search_history`, 조회·삭제는 로그인 필요, **구현됨**)

`search_history`는 사용자 기록이면서 이용 통계(검색 수, 인기 출발지·목적지)의 원본이다. 그래서 행을 고치거나 지우지 않는다.

- **저장은 서버가 자동으로 한다.** `GET /api/routes`가 성공(`200`)했을 때만 저장한다. 프론트는 저장 요청을 보내지 않는다 (`POST /api/history`는 없다).
- **조회할 때 같은 검색을 묶는다.** 기준은 (출발지 이름, 목적지 이름, 도착 희망 시각의 시:분, KST)이고, 묶음마다 가장 최근 것 하나가 카드가 된다. 이름은 대소문자를 구분하고, 여유시간은 묶음을 나누지 않는다.
- **삭제는 분리다.** 행의 `user_id`를 `NULL`로 바꿔 내 목록에서만 사라지게 한다. 통계 행은 남는다. 탈퇴할 때도 같다 (`ON DELETE SET NULL`).
- 사용자에게 연결된 행은 최근 200개까지 유지하고, 넘으면 오래된 것부터 분리한다.

### 자동 저장 (`GET /api/routes`)

| 상황 | 저장 |
| --- | --- |
| `200` 응답 (일부 옵션만 성공한 경우 포함, 응답 캐시 적중 포함) | 저장 |
| `400`, `422`, `5xx` 등 실패 응답 | 저장 안 함 |
| 로그인 사용자 | `user_id` = 세션 사용자 |
| 비로그인 | `user_id` = `NULL` (통계용. 누구의 목록에도 나오지 않는다) |
| 로그인 사용자가 같은 검색(위 묶기 기준)을 **5분 안에** 다시 함 | 저장 안 함 (새로고침·뒤로 가기). 5분이 지나면 새 행 |
| 비로그인 사용자의 반복 검색 | 매번 저장 (같은 사람인지 알 수 있는 값을 저장하지 않으므로 묶지 않는다) |

- 저장 값: 출발지·목적지 이름(공백 정리, 100자까지), 실제로 경로 계산에 쓴 좌표(소수 7자리. 이름으로 확정한 경우 그 좌표), 도착 희망 시각, 여유시간, 추천 카드의 권장 출발 시각(추천 카드가 없으면 `NULL`), 이동수단 `car`. `ai_summary`는 `NULL`.
- 저장은 응답을 보낸 뒤 백그라운드에서 한다. 세션 확인·저장이 실패해도 경로 응답에는 영향이 없다 (서버 로그에만 남는다).
- **개인정보:** 비로그인 검색도 통계용으로 저장된다. 저장하는 값은 위의 검색 조건(출발지·목적지 이름과 좌표, 도착 희망 시각, 여유시간, 권장 출발 시각, 이동수단)과 저장 시각뿐이며, 비로그인 사용자를 식별할 수 있는 값(IP, 쿠키, 기기 정보)은 저장하지 않는다. 로그인 사용자가 기록을 지우거나 탈퇴하면 같은 상태(식별자 없는 통계 행)가 된다. 개인정보 처리방침에 이 내용을 적는다.

### GET /api/history?limit=

로그인: **필요**. 최신순, 묶은 뒤 `limit`개 (기본 20, 1~50 정수). 그 밖의 값(`0`, `51`, `abc`, `1.5`, 빈 값)은 `400` "개수는 1~50 사이의 정수여야 합니다."

```json
[
  {
    "id": "12",
    "from": "김해시청",
    "to": "동의대학교",
    "arriveTime": "2026-11-02T09:00:00+09:00",
    "buffer": 10,
    "departTime": "2026-11-02T08:12:00+09:00",
    "fromLat": 35.2285, "fromLng": 128.8894, "toLat": 35.1441, "toLng": 129.0336
  }
]
```

- `id`: 묶음의 대표(가장 최근) 행. 삭제에 쓴다.
- `departTime`, 좌표: 없으면 `null`. 다시 검색할 때 `buffer`와 좌표를 함께 넘기면 장소 확정을 건너뛴다.
- 매핑: `from` = `origin_name`, `to` = `dest_name`, `arriveTime` = `arrive_at`, `buffer` = `buffer_min`, `departTime` = `recommended_depart_at`, `fromLat`… = `origin_lat`…

오류: `400`, `401`

### DELETE /api/history?id=

**카드 한 장**(그 `id`와 같은 검색 묶음 전체)을 내 목록에서 지운다. 묶음 안의 어느 행 `id`로 지워도 같다. 응답: `204`

오류: `401`, `404`(없음, 남의 것, 이미 지운 것, 숫자가 아닌 `id`. `id=`가 비어 있어도 전체 삭제로 넘어가지 않고 `404`)

### DELETE /api/history

`id` 없이 보내면 내 기록 **전체**를 지운다. 지울 것이 없어도 `204`. 오류: `401`

## 해민과 정할 것

### [해민과 합의 필요] 출발시각 API (`POST /api/departure`)

1. **필드 표기**: 이 API만 snake_case(`recommended_depart_at`)이고 나머지 명세와 프론트는 camelCase(`departTime`)다. 둘 중 하나로 통일한다. camelCase로 맞추면 서버에서 별칭(alias)만 바꾸면 된다.
2. **`/api/routes`와의 관계**: (나)로 구현했다. `GET /api/routes`가 경로 옵션마다 이 엔진으로 `departTime`을 계산한다. `POST /api/departure`는 단일 계산용으로 남긴다.
3. **좌표 전달**: 이 API는 좌표가 필수다. 지금 검색 조건 URL 쿼리(`from`, `to`)에는 장소 이름만 있어서, 결과 화면이 좌표를 알려면 쿼리에 좌표를 더하거나 장소 id로 다시 조회해야 한다.
4. **개발 환경 주소**: 프론트 `config.js`의 `BASE_URL`은 `/api`(같은 출처)다. Live Server(5500)와 uvicorn(8000)을 따로 띄우면 `http://127.0.0.1:8000/api`로 바꿔야 한다. 배포 때는 같은 출처로 두면 CORS가 필요 없다.
5. **오류 코드**: 입력 오류 400, 계산 불가 422, 외부 API 오류 502/503/504. 프론트는 4xx의 `message`를 그대로 보여 주고 5xx는 일반 문장으로 바꾼다 (지금 `api.js` 동작과 같다).

### [해민과 합의 필요] 경로 비교 (`GET /api/routes`)

1. **`js/mock/routes.json` 갱신**: `id`가 `route-1` 형식에서 `recommend` 등 옵션 키로 바뀌고 `options`, `bufferApplied`, `converged`가 생겼다. 목업을 바꾸면 `js/mock/routeGraph.json`의 `routeId`도 같이 바꿔야 그래프가 계속 짝지어진다.
2. **합쳐진 카드 표시**: `options`가 2개 이상이면(예: 추천 = 최단시간) 태그를 "추천 · 최단시간"처럼 보여 줄지.
3. **`bufferApplied=false` 안내**: 지금 카드는 요청한 여유시간을 항상 "여유 10분"으로 표시한다. 반영하지 못했을 때 "여유시간 미반영"을 보여 줄지.
4. **카드 4개**: 태그 색(`tag-3`)과 지도 색(`ROUTE_COLORS`)이 3개까지만 있다. 4번째 카드의 색을 정한다.
5. **색 기준**: 지금 색은 카드 순서(index)에 붙는다. 옵션(`id`)마다 색을 고정할지.
6. **빠진 옵션 안내**: 빠진 옵션과 이유는 서버 로그에만 있다. 화면에 "무료도로 경로 없음" 같은 안내가 필요하면 응답 형식을 다시 정한다.

### 그 밖의 항목

- 장소 검색 호출 방식: 프론트엔드가 장소 검색 API를 직접 호출할지, 백엔드 `GET /api/places`가 중계할지 (해민과 합의 필요)
- `from`, `to` 형식: 지금은 장소 이름만 전달한다. 출발시각 계산에는 좌표가 필요하다 (위 3번).
- `aiSummary`를 `/api/routes`에 포함할지, 별도 API로 분리할지

### 정해진 항목 (즐겨찾기·검색 기록)

- 즐겨찾기 좌표: 프론트가 장소 검색에서 고른 `lat`·`lng`를 함께 보낸다. 없으면 서버가 찾고, 못 찾으면 `400`.
- 응답 필드: 즐겨찾기에 `lat`·`lng`, 검색 기록에 `buffer`·`departTime`·좌표를 더했다. 프론트 mock JSON도 같은 필드로 맞춘다.
- 검색 기록 저장: 서버가 `GET /api/routes` 성공 때 자동으로 한다. `POST /api/history`는 만들지 않았다.
- 비로그인: 즐겨찾기·기록 API는 모두 `401`. 프론트는 비로그인이면 부르지 않는다. 로컬 저장은 하지 않는다.
- 검색 기록 삭제는 카드 단위(같은 검색 묶음)이고, 행은 통계용으로 남는다 (`user_id` NULL).

### 정해진 항목 (회원)

- 소셜 로그인 경로: `GET /api/auth/{google|kakao}/start`, `/callback` (위 "소셜 로그인"). 프론트 `SOCIAL_AUTH_START_URLS`에 `start` 경로를 넣는다.
- 소셜 로그인 결과: `/pages/search.html?auth_result=success|cancelled|email_exists|failed`
- 같은 이메일의 소셜 계정은 자동 연결하지 않는다 (`email_exists`).
- 소셜 가입의 약관 동의: 로그인 모달 안내 문구를 동의로 보고 `agreed_at`에 가입 시각을 넣는다.
